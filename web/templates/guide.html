EJEMPLO INTEGRADOR

Access Control Lab: cómo se conecta todo

Ana · Diego
ACTORIdentidad: Ana

La cuenta/persona que hace requests. Puede renovar cookie o Bearer y seguir siendo la misma Identidad.

/me.id = 101
COSAObjeto de negocio: Order 123

La entidad estable sobre la que Ana o Diego actúan.

/api/orders/123 · orderId=123
PROPIEDADownerId = 101

Describe ownership del Order. Puede relacionarlo con Ana, pero no debe convertirse automáticamente en resolver de identidad.

Order 123 → ownerId 101
HISTORIAFlujo

La secuencia de Requests que forma una acción de negocio.

order → invoice → cancel
  1. Inventario. Mantienes app.accesslab.local y api.accesslab.local en alcance y no mezclas score.accesslab.local.
  2. Contextos de identidad. Creas Ana y Diego. Una request de /me puede enseñarte que id=101 y el email resuelven a Ana.
  3. Buscar / Seguir valor. Sigues 101, ownerId o orderId=123 para descubrir en qué otras requests reaparecen.
  4. Buscar relacionados. Unes por evidencia /api/orders/123, /invoice y /cancel. Esto crea contexto, no una vulnerabilidad.
  5. Authorization Matrix. Comparas la misma superficie con Ana/Diego/Anonymous. Si los Orders ajenos suelen dar 403 pero un endpoint da 200, ya tienes algo que investigar.
  6. Comparación inteligente. Abres las dos Requests y separas lo importante: auth cambió, orderId no, status/response sí.
  7. Flujo. Si el caso es method bypass, multi-step o Referer, capturas el recorrido normal y una variante. Comparación de Flujos te enseña pasos ausentes/cambiados.
  8. Objeto de negocio. Enseñas Order: orderId. Desde entonces Negro entiende que 123 es la misma instancia aunque aparezca en path, body o distintos endpoints.
  9. Hipótesis → Hallazgo. Sólo después de reproducir impacto promueves la evidencia a hallazgo.

FASE 1 · SUPERFICIE

Inventario y enumeración

Pregunta central: ¿qué existe y qué me falta revisar?

Inicio

Resumen del proyecto, progreso, señales y trabajos recientes. Úsalo para orientarte, no para investigar un endpoint en detalle.

Lab: ver cuántos hosts/rutas ya entraron y si quedó trabajo pendiente.

Inventario

Lista persistente de hosts y recursos con estados humanos. Te permite marcar pendiente, revisado, interesante o revisitar.

Lab: app/api están in-alcance; scoreboard queda fuera.

Herramientas del host

Inspección básica: DNS/HTTP/TLS. Recon web: robots/sitemap/.well-known. Crawler: enlaces navegables. JS: bundles. TLS SAN/DNS pasivo: nombres relacionados. CORS/VHost: comprobaciones puntuales.

Lab: Recon web puede descubrir /.well-known/openid-configuration.

Ejecuta una herramienta porque responde una pregunta; no por llenar métricas.

Resource / Operation / Request

Resource es la ruta. Operation es método+ruta. Request es una llamada HTTP concreta observada junto con su response.

Resource /api/orders/123 → GET → Request #442

Esto evita confundir “el endpoint” con una única request histórica.

CATÁLOGO · HOST

Qué hace cada herramienta de enumeración

Inspección básicaConfirma DNS A/AAAA/CNAME, HTTP/HTTPS y TLS. Úsala para saber si el host realmente responde y cómo.
Recon webRevisa raíz, robots.txt, sitemap y rutas .well-known. Úsala para superficie publicada/estándar.
Crawler controladoSigue enlaces navegables dentro del alcance. Úsalo cuando una aplicación tiene rutas enlazadas que aún no están en inventario.
Descubrir JavaScriptEncuentra bundles/scripts cargados. Luego el análisis local puede extraer rutas, URLs, websockets y configuraciones.
TLS SANLee nombres del certificado. Sirve como pivot de nombres relacionados; no confirma que todos estén in-alcance.
DNS pasivoConsulta historial cuando hay proveedor configurado. Úsalo para nombres/IP históricos, siempre filtrando por alcance.
CORS en raíz/recursoEnvía un Origin controlado y observa ACAO/credenciales. En endpoints concretos, prueba desde Resource para conservar mejor contexto.
VHost inteligenteCompara respuestas por Host contra una base conocida. Úsalo cuando tienes una IP/base y candidatos de hostname autorizados.

FASE 2 · EVIDENCIA

Buscar, seguir y comparar

Pregunta central: ¿dónde vive esta pista y qué conecta?

Buscar

Entrada universal cuando ya tienes texto o contexto.

ownerId · 101 · X-Original-URL · host:api... method:GET

Lab: buscar ownerId encuentra todos los recursos que hablan de ownership.

Explorador de parámetros

Agrupa campos observados por nombre, ubicación, valores y frecuencia.

Lab: diferencia /me.id=101 de orderId=123 y ownerId=101.

Que dos campos terminen en “Id” no los vuelve equivalentes.

Seguir valor

Sigue un valor exacto aunque cambie de nombre o ubicación.

101 → /me.id → ownerId → response.user.id

Útil para entender propagación de IDs sin asumir semántica.

Buscar relacionados

Toma valores útiles de una Request y busca otras Requests con coincidencias fuertes.

/orders/123 ↔ /orders/123/invoice

“Relacionado” significa evidencia compartida, no causalidad.

Comparación inteligente

Compara dos requests/responses y separa ruido de diferencias de negocio.

Ana / orderId=123 / 200 ↔ Diego / orderId=123 / 403

Ideal después de reenviar con otra Identidad o usar la Matriz de autorización.

FASE 3 · ACTORES

Contextos de identidad y autorización

Pregunta central: ¿quién hizo esta request y qué cambia con otro actor?

Contextos de identidad

Una Identidad es estable; su cookie/Bearer puede rotar. Los resolvers son valores estables del actor, como /me.id, email o jwt:sub.

Lab: Ana sigue siendo Ana aunque cambie session=....

ownerId, orderId y tenantId describen contexto/objetos; no deben identificar automáticamente al actor.

Authorization Matrix

Resume evidencia observada por identidad y operación.

/orders/123 · Ana 200 · Diego 403 · Anonymous 401

Si /invoice devuelve Diego=200 mientras endpoints vecinos dan 403, la excepción merece Repeater.

No observado ≠ permitido/denegado.

FASE 4 · HISTORIAS

Flujos y estados de negocio

Pregunta central: ¿qué secuencia ocurrió y cómo cambia una variante?

Captura de Flujo

Iniciar Flujo abre una ventana de captura. Todas las requests entran como candidatas; después eliges Include/Ignore, Start y End.

Lab: captura un proceso multi-step administrativo o una secuencia Order → invoice → cancel.

Comparación de Flujos

Alinea referencia base y variante y muestra pasos ausentes, extra, cambiados, identities, status y estados.

Lab: compara POST normal con variante de método o un bypass que omite un paso de autorización.

Estado de negocio

Enseña una definición como Order = orderId + status y Negro sigue estados por instancia.

Order 123 · CREATED → PAID → SHIPPED

Una transición diferente es observación, no “payment bypass” automático.

¿Qué es un Objeto de negocio?

Una entidad estable del dominio: Order, User, Invoice, Payment, Shipment, Cart. La reconoces por uno o varios nombres de campo.

Order: orderId + order_id + path /orders/:id

Lab: Order 123 sigue siendo el mismo Order en /orders/123, /invoice y /cancel.

¿Qué NO es?

No es “cualquier id”. Un roleId, contador, feature flag o identificador efímero puede no merecer un objeto. La sugerencia sólo dice “este campo parece identificador”.

Tú decides si el concepto tiene significado estable.

Cross-host correlation

Si el mismo tipo+valor aparece en hosts distintos, Negro muestra una sola instancia con todo su historial.

Order 123 → api → invoice service → shipping

Anomalías de patrón

Compara una instancia con patrones que ya se repitieron en peers.

Diego: 403, 403, 403 → Order 123 invoice: 200

La anomalía es “resultado distinto al patrón”, no “IDOR confirmado”.

FASE 6 · PRIORIZAR Y DOCUMENTAR

Señales, inteligencia, investigación y hallazgos

Señales / Notificaciones

Observaciones automáticas con evidencia concreta. Te dicen “mira esto”.

Señal ≠ vulnerabilidad.

Reglas personalizadas

Patrones del negocio que tú le enseñas a Negro. Todas las condiciones rellenadas deben cumplirse y la coincidencia conserva la Request exacta.

Identidad presente + parámetro ownerId → Señal

Uso: recuerda pruebas recurrentes como comparar identidades, Seguir valor o revisar un header propio del proyecto.

Tu regla reconoce hechos; no decide si hay IDOR, bypass o impacto.

Mapa con inteligencia asociada

Endpoints y Requests con Señales o Hipótesis se resaltan. Al abrir su detalle aparece Inteligencia asociada con enlaces directos al Señal o Hipótesis exacto en Investigación.

GET /orders/4101/invoice · S1 · H1

Uso: mientras exploras el grafo puedes detectar de inmediato qué rutas ya tienen una pista o una hipótesis pendiente.

Intelligence

Concentra reglas determinísticas y pistas de HTTP/JS/recon para que no se pierdan.

Lab: headers alternos, IDs controlables, method variation o redirects pueden convertirse en pistas.

Investigación / Hipótesis 2.0

Pregunta comprobable que reúne evidencia y propone una siguiente prueba manual. El motor puede correlacionar Identidad, Flujo, Objeto, Estado, Señales, anomalías y resultados HTTP entre identidades.

¿/invoice valida ownership o sólo conocimiento de orderId?

La IA sólo genera hipótesis cuando tú la ejecutas; nunca convierte una correlación en hallazgo automáticamente.

Hallazgos

Registro de algo ya confirmado: impacto, evidencia, entidades afectadas y retests.

Es la última etapa, no la primera.
